# 游戏发布执行规范

本规范适用于已有游戏更新、新游戏首发、未完成发布的恢复及回滚。后续发布任务必须先读本文件，再按 [现行命令说明](CODEX_RELEASE.md) 执行。涉及授权、凭据、生产和文件保护的边界同样适用。

## 1. 完成标准与实现边界

发布必须区分四项证据：源码已推送、GitHub 构建通过、EdgeOne 已部署、正式域名验收通过。任何一项未知，都不能用其他项代替。

当前 GitHub Actions 和 EdgeOne Git 集成分别接收平台推送。GitHub 的构建产物上传不负责启动 EdgeOne 部署，构建通过不能证明托管端已收到任务。

当前脚本已经提供认证预检、游戏与聚合检查、推送、正式版本等待和生产 smoke。以下规范中的云任务阶段识别、断点恢复、按尝试归档和受控重试，尚未全部实现为脚本功能，须由执行者补做并留证。**不得使用不存在的 `--resume`、`--retry` 等参数，也不得宣称规范文档等于自动化已经完成。**

## 2. 发布前

1. 确认用户已授权本次 GitHub 写入和正式上线；范围内授权持续有效，不重复询问。首次公开建仓或披露此前非公开数据、素材时，先明确目的地及内容范围。
2. 核对最新远端 `main`、本次改动清单和工作区状态。已有无关改动必须保留；复杂或脏工作区使用独立干净副本，不用破坏性 Git 操作清场。
3. 固定来源仓库、完整游戏 SHA、注册表、构建参数及产物版本；保存上一个已验证生产平台 SHA 和全部游戏 refs。
4. 明确回滚目标及可取得的产物。不得只准备游戏旧数据而遗漏配套 JS、CSS、注册表和共享资源。
5. 先执行 dry-run，再执行正式发布。有未提交的本次游戏文件时，两次命令都逐个指定 `--file=相对路径`。

```sh
npm run release:game -- <game-id> --dry-run
npm run release:game -- <game-id>
```

`<game-id>` 和下文 `<platform-sha>` 为占位符。游戏本地检查和远端聚合检查的版本范围，遵循 [CODEX_RELEASE](CODEX_RELEASE.md)。不可将尚未推送的本地改动说成已被远端聚合验证。

## 3. 正常发布

1. 使用正常登录用户的现有安全 Git 凭据做非交互预检；不输出凭据，不因网络失败直接要求重新登录。
2. 完成游戏 test、可用时的 typecheck、build，推送并核对远端游戏 SHA。
3. 只更新本次目标游戏的注册表 ref；完成公开锁定来源的聚合测试、构建和 validate。
4. 推送平台后记录目标平台 SHA、对应 GitHub run 和正式域名原版本。
5. 等待正式域名版本匹配，再执行 smoke。正常路径不要求用户提供云部署 ID 或操作控制台。
6. 检查对应 GitHub run 的完整状态；build、production-smoke 和人工/独立运行的验收结果分别记录。未知状态必须保留为未知。

## 4. 版本没有更新时先分类

不要反复等待同一个旧 SHA，也不要直接归咎于游戏代码。设置独立的触发检查窗口，建议初始值为推送后 90—120 秒，再根据实际数据调整。

- 有可靠的云任务状态来源：核对目标 SHA 是否生成任务，记录任务 ID 和排队、克隆、构建、发布阶段。
- 无法读取云任务状态：标记 `DEPLOYMENT_STATUS_UNKNOWN`。正式站仍旧只能证明版本没更新，不能证明任务未生成。
- 已确认任务不存在：标记 `DEPLOYMENT_TRIGGER_MISSING`，检查关联仓库、生产分支、自动部署开关及触发记录，再评估受控重试。
- 已存在失败任务：保存实际错误与日志，修复具体原因。不得创建空提交掩盖明确构建错误。
- 云端显示发布成功但正式站版本不符：检查路径、元数据、缓存与域名指向；不要直接放宽版本判定。

无异常时不重复审核 DNS、SSL、CloudBase 或全部云配置。需要新服务权限、令牌、收费或 DNS 变更时，先明确具体影响并取得相应授权。

## 5. 任务缺失时的受控重试

既有正式上线授权覆盖同一内容、同一生产目的地的非破坏性重试。**每个发布目标最多重试一次**，不得循环制造提交。

重试前须同时满足：

- 远端已确认收到原平台提交。
- 通过可靠记录确认目标 SHA 没有对应云任务；只有旧生产版本或状态接口不可用，不满足此条件。
- 没有其他发布正在进行，也没有更新的目标取代本次提交。
- 独立工作副本干净，游戏 refs、注册表及内容树与已验证目标一致。
- 已记录原始目标、失败阶段、重试原因和上一个已验证生产版本。

保留 Git 自动部署方式时，可使用一次不改变文件的发布触发提交。必须验证原提交和重试提交的 tree SHA 相同、文件差异为空，推送前再次核对远端未移动，并记录两次完整平台 SHA。只允许正常快进推送，不使用 force push。

重试后按新的目标 SHA 重新确认任务、正式版本和 smoke。再次没有任务则停止重试，保存证据并报告外部触发链阻碍。不得关闭安全设置、手动上传 EdgeOne 产物或删除旧部署绕过失败。

## 6. 恢复与重复执行

当前 `release-game.mjs` 在注册表 ref 未变化时可能返回 `already-current`。这不是正式站已更新的证明。

重复执行之前先读取之前的发布记录，核对远端平台 SHA、游戏 refs 和正式域名：

- 正式版本已经匹配：补跑尚未完成的 smoke 或 CI 状态核对，不再推送或部署。
- 注册表已更新而生产仍旧：按第 4、5 节恢复，不把脚本的 `already-current` 当作发布成功。
- 游戏已推送但平台注册失败：复用已核对的游戏 SHA，修复平台步骤，避免重复游戏提交。
- 原目标已被更新的发布取代：记录 `SUPERSEDED`，重新核对当前目标，不继续等待旧 SHA。
- 权限或审批不可用：保存检查点，不绕过审批，也不从头重复已完成的外部写入。

现有只读验收入口如下，目标 SHA 必须先核对：

```sh
node scripts/wait-production.mjs <platform-sha>
node scripts/smoke-production.mjs
```

## 7. 统一状态与证据

这些是执行与报告约定，不能伪装成现行脚本已经输出的全部枚举值：

| 状态 | 必须具备的判断依据 |
| --- | --- |
| `PUSHED` | 远端完整 SHA 已核对 |
| `DEPLOYMENT_STATUS_UNKNOWN` | 缺少可靠云任务状态来源 |
| `DEPLOYMENT_TRIGGER_MISSING` | 可靠记录确认没有目标任务 |
| `QUEUED` / `BUILDING` / `DEPLOYING` | 对应任务的实际阶段 |
| `CLOUD_BUILD_FAILED` | 明确失败任务及错误日志 |
| `VERSION_MISMATCH` | 正式域名元数据与目标不符 |
| `SMOKE_FAILED` | 版本匹配但线上验收失败 |
| `ACCESS_BLOCKED` | 具体操作所需权限不可用 |
| `REVIEW_UNAVAILABLE` | 审批服务未能完成审核 |
| `SUPERSEDED` | 已识别更新的发布目标 |
| `VERIFIED` | 正式版本、全部 refs 与线上 smoke 通过 |

GitHub 远程作业汇总状态单列；独立 smoke 通过不能冒充远程 CI 成功。存在待核实项时，说明已通过什么、仍缺什么，不笼统写“全部通过”。

报告写入忽略目录，建议 `reports/releases/<release-id>/attempt-01/`、`attempt-02/` 分别归档；现行 `reports/release-latest.json` 只作为最新索引/摘要，不覆盖唯一历史证据。记录：

- 改动范围、来源 SHA、目标平台 SHA、游戏 refs、构建/数据版本。
- 各阶段结果和时间、CI run、可取得的云部署任务 ID。
- 正式元数据、资产完整性、HTTP/路径/缓存检查、smoke 和必要的玩法截图。
- 失败原文的脱敏摘要、未核实项、重试关系、检查点和回滚目标。

不得把令牌、Cookie、授权头、环境文件、账号登录资料或包含这些内容的原始日志写入报告。没有取得供应商投递日志时，事件未触发的内部原因保持未证实。

## 8. 线上验收与用户交付

- `release-meta.json` 的平台 SHA、全部启用游戏 refs 必须与本次目标一致。
- 验证入口、子路径直接访问与刷新、JS/CSS/JSON/图片 MIME、真实 404、共享资源、缓存与版本一致性。
- 运行生产 smoke，自动化和 smoke 必须遵守现有埋点排除契约；未经批准不启用新事件。
- 涉及游戏逻辑或数据时，补做对应关键行为/结果对账，保留冻结成果和质量隔离规则。
- 截图前等待关键图片完成加载/解码；浏览器模拟、真机及大陆网络覆盖分别报告，不相互替代。
- 报告游戏提交、平台提交、正式版本、CI 状态、线上验收及剩余限制，并提供正式入口和回滚方式。

一次发布遇到浏览器同类控制错误时，应尽早停止重复重连。优先使用已有的、经授权的只读状态接口；确需人工协助时，一次说明要提供的具体页面或信息，不把常规发布变成反复登录、重启和引用标签页。

## 9. 首发与基础设施变更

新游戏首次接入先完成 [新游戏清单](NEW_GAME_CHECKLIST.md) 和 [接入协议](GAME_INTEGRATION.md)，明确注册项、图标、路径、构建命令及完整锁定 ref，独立验证后再聚合。常规 ref 更新脚本不能被当作首发全部适配已经自动完成的证明。

部署来源、API 权限、域名或构建体系变化按基础设施任务处理。新增状态查询能力前须核实当前 Git 项目的接口支持和真实权限范围，不索取控制台 Cookie，也不假定令牌具备细粒度只读权限。

回滚恢复完整且相互匹配的平台版本、全部游戏 refs 与静态资源，通过既有验证和发布链路执行；不只隐藏入口或替换单个 JSON。自动回滚条件须事先约定，不因排查不便就破坏当前正常版本。

## 10. 后续脚本改造的验收要求

文档入仓不代表以下功能已经实现。开发发布编排时，至少验证：

1. ref 相同而生产仍旧，不提前报告已发布。
2. 构建成功但任务缺失，能够识别；状态不可读时保持未知。
3. 受控重试最多一次，内容树不变，并处理重复/过期任务。
4. 云构建失败有日志，不以空提交无限重试。
5. 正式版本或资源错配、smoke 失败均不通过。
6. CI 查询、云权限、审批不可用分别归类，并可从检查点续跑。

依据：2026-10-16 Coin 0.4.3 首发中，首次推送未观察到对应 EdgeOne 任务；相同内容的一次 Git 重试随后自动部署成功。该事实用于改进恢复流程，不作为供应商内部故障归因。
